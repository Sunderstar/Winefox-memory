数据流与运行原理
原始记录始终存在
终端、QQ、Minecraft 的原始聊天文件位于 data/chat_history.jsonl，自主发言位于 data/autonomous_history.jsonl。程序读取原文进行提炼，从不删除已处理记录。你在工作台对话文本的编辑只影响冻结的实验副本。
为什么正常提炼会跳过已经处理的消息？
正常的 memory-extract 会查询 SQLite 表 processed_records，过滤已经成功提炼的消息 ID。这只是为了不重复消耗 API，不意味着删去原文，也不意味着全局语义去重。必要时可通过命令行的 --reprocess 重做。本工作台的固定样本实验完全不更新 processed_records，因此允许你在相同消息上反复测试不同模型。
分阶段输入和输出
冻结样本：勾选和编辑后的消息 → ui_samples 表中的不可变记录，以及当时的已有记忆快照。
Stage 1：冻结原文 → Episode 事件（标题、summary、detail、计划和证据 ID）。
Stage 2：原文 + Episode → Cand 事实/约定/偏好/计划候选。
可选 Stage 3：原文 + 两阶段结果 → 核验报告，仅作审核建议，不自动修改或反复重试。
审核：人工修改/同意/拒绝 → 正式记忆。
具体存储位置
SQLite 文件 data/memory.db：extraction_runs 记录输入、模型、提示词、原始回复与 Token 用量；extracted_episodes 与 episode_plans 保存事件和计划；candidates 保存待审批短事实；memories 保存已批准事实；candidate_episode_links 保存两者关系；ui_samples 和 ui_sample_runs 保存实验快照与运行关联；ui_edit_history 保存界面编辑历史。人工编辑不会覆盖模型原始输出。
回答时怎样召回？
程序从正式事实记忆和已批准 Episode 检索相关内容：普通问题先使用短摘要，询问过程时展开 Episode 详情，询问原话时再加载 Raw。人工已批准及经启用的 AI 自动归档（auto_active）可参与召回；未启用自动归档时的 pending 草稿不参与召回。自动可用不表示人工验证。
重要限制
本界面是本机工具，不支持公网部署和多人协作。实验样本编辑后产生的是“反事实/修订语料”测试，必须区分于真实原话；如需严格事实核对，应使用未修改的原始文本。模型调用存在实际费用。批量审批会逐条执行，有错误时返回具体错误而非整批回滚。工作台不直接修改 persona.md。
